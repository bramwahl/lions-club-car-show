# Phase 1B completion report

Implementation and validation are finished. **One project configuration step remains:** disable general Supabase self-signup. The public Auth settings endpoint still returned `disable_signup=false` at final verification. The project secret cannot change management settings, and the available dashboard session was signed out. The operator was asked to turn off Authentication → Sign In / Providers → User Signups → Allow new users to sign up. Unassigned Auth users have no application role/access; the implemented Admin provisioning flow independently creates confirmed users without email.

1. **Auth architecture:** Supabase email/password with SSR cookies, proxy token refresh, verified `getUser`, fresh active-profile authorization in every protected page/action and independent database checks. Sign-in/sign-out and the minimal public, staff, Judge and Admin shells are implemented.
2. **Exact roles:** `admin`, `judge`; Public has no role. No Captain/entrant roles, metadata-based authority or historical WordPress Auth accounts.
3. **RLS:** enabled on all seven tables; 17 policies. Admin-only raw business reads, self/Admin profile reads, constrained Admin event/participant/car/registration writes; no direct client score/history/profile mutations. See [security state](security-state.json) for exact names and [architecture](README.md) for column permissions and RPCs.
4. **Privileged server operations:** confirmed Auth createUser and compensating deletion only in the app, after fresh Admin authorization. Operator bootstrap, migrations and isolated test cleanup are separate tooling. Ordinary data calls use public credentials plus JWT.
5. **Account management:** list, create Judge/Admin, set initial password, change name/role, activate/deactivate. Existing JWTs lose authority on deactivation/role changes. Last-active-Admin protection is enforced in the database. One active initial Admin remains; all temporary test accounts are removed.
6. **No-email approach:** `auth.admin.createUser({email,password,email_confirm:true})`. No invitation, signup, confirmation, OTP, welcome or password-setup call. Transport contract tests confirm Admin creation endpoint use; the remaining Admin is confirmed and has no `confirmation_sent_at`. Password fields clear after submission; server responses contain no password. The temporary bootstrap password was removed from ignored `.env.local` after testing; the actual Auth password is unchanged.
7. **Public exposure:** only explicitly enabled event metadata and whitelisted vehicle snapshot/score projections. No participant directory, contact enumeration, email/phone/address fields or anonymous participant SELECT. Future participant matching requires a separately approved narrow server workflow with enumeration protection.
8. **Judge permissions:** active new event and minimal registration/vehicle/score/history queries; any of the six original sections; registration-owned Lions Choice votes. No Admin access, role management, payments, Quick Edit, persistent-car/participant edits, direct history writes or generated-total manipulation. Attribution comes from `auth.uid()`.
9. **Admin permissions:** full business-table visibility under RLS; approved event/participant/car/registration management permissions and atomic Quick Edit; account management UI. Complete business workflow interfaces remain deferred. Imported deletion and reopening legacy judging were not enabled.
10. **Tests:** 15/15 local tests, including all 13 prior tests; live Supabase JWT/RLS tests; authenticated HTTP routes and forged Server Actions; browser sign-in/account creation/Judge denial/sign-out; client artifact secret scan; target numeric validation in a rolled-back transaction.
